# Stick Skirmish

双人局域网 3D 第三人称射击。目标场景：两台笔记本各占一块全屏，同一网络，浏览器打开就能玩。

## 环境

- Godot `4.7.2-stable`：`D:\Tool\Godot\4.7.2\Godot_v4.7.2-stable_win64.exe`
- 导出模板只装了**网页平台**（`%APPDATA%\Godot\export_templates\4.7.2.stable\`）

## 渲染器

项目锁定 **Compatibility（WebGL 2）**。Godot 4 的网页版不支持 Forward+/Mobile，
所以本地编辑器里看到的画面就是浏览器里能得到的上限，不要往更高画质上调。

## 美术风格：黑白线稿

整套画面是**墨水画在纸上**：纸白的面、墨黑的线，没有任何彩色。
颜色只在一个地方定义（`scripts/ink.gd`），因为“去色”最容易漏的就是某一处，
而漏了不会报错，只会有一个部件还有颜色。

| 对象 | 做法 |
| --- | --- |
| 场地墙面、地板、掩体 | 纸白的方盒 + **每一道棱与每一个角**都画墨线（细长方条）。棱线取“整边 + 线宽”，所以转角处会互相搭上，再叠一个角标加粗，形成手绘的“积墨” |
| 地板 | 方格纸式的 4 米网格。一片白地没有任何深度线索，判断不了距离；而它同时也就是“手绘”的一部分 |
| 角色 | 肢体是**胶囊**（不是细杆），直径 6~8 厘米，两端是半球——看起来是根有体积的短棍，而不是一条线 |
| 角色的墨线 | **反壳描边**：把网格沿法线放大、并反转面剔除，于是只在轮廓外沿露出一圈。对圆柱、球、胶囊都自动成立，不用为每种形状再造一个描边网格 |
| 枪 | 枪管与机匣取**深色**、握把那一系纸白：白手上一把黑枪才看得出手里有东西（反过来就是一小团白） |
| 头上的血条 | 墨色底 + 纸白填充，长度就是血量。墨底比填充大一圈，那一圈就是它的描边 |
| 界面（准星、血量、比分、横幅） | 只有纸白与墨（`INK`）/石墨（`GRAPHITE`）两三个灰度，不再用色相区分主次 |
| 光照 | 白环境光 + 白面光、**完全不投影**。明暗只由朝向产生，那点浅灰就是“铅笔的排线”；硬阴影会在白墙上压出一片灰，与“画上去的线”不是一回事 |

### 黑白里怎么区分两个玩家

旧配色靠橙/青的色相差，去色之后两者都是白，必须换一套：

| 序号 | 名称 | 黑白里能看到的差别 |
| --- | --- | --- |
| 0 | `ember` | 头是**实心墨块**（白眼睛），肢体略粗，墨水色是墨黑 |
| 1 | `frost` | 头是纸白带墨线（黑眼睛），多一道胸前墨带，肢体略细，墨水色是石墨灰 |

“墨水色”决定的是**弹道与命中特效的深浅**，所以能分辨一串线是谁打出来的。
`tools/art-check.gd` 会断言两者在这些属性上都不同、而且全部是灰。

### 绘制批次与碰撞

17 个掩体 × (1 个面 + 20 条线) 会是 350 多个 `MeshInstance3D`，在 WebGL2 下全是独立的
绘制调用。所以场地的面与线**各合并成一个网格**（用 `SurfaceTool.append_from` 拼方盒），
无论加多少掩体，场地都只有 2 个绘制调用；`art-check.gd` 里有一条断言守着这个数。

外观与碰撞是分开的：外观是纯视觉的 `MeshInstance3D`，物理形状仍是一盒一个 `StaticBody3D`。
地板网格线特意没有碰撞——它是画上去的线，不是地上的凸起，有碰撞会让射线打在
离地 8 毫米的“线”上。

### 还没做的

线仍然是**完全笔直**的。手绘最明显的特征是线条的欹侧与粗细变化，
但那需要让线条不规则；在远处它会变成令人烦躁的抖动，所以先留白。
如果要做，正确的位置是 `arena.gd` 的 `_add_box_marks`（给每条线一点确定性的随机偏移）
与角色的描边宽度（按骨骼位置微调 `grow_amount`）。

## 局域网怎么跑

```powershell
node tools/serve.mjs
```

会同时监听两个端口：HTTP（默认 8000，**只有本机能用**）和 HTTPS（默认 8001，**另一台设备用这个**）。

### 为什么另一台设备必须走 HTTPS

Godot 4 的网页版要求页面处于 **Secure Context**。浏览器只把 `localhost` 和 `https://`
算作安全上下文，**明文 HTTP 的局域网 IP 不算**，引擎会直接拒绝启动并报：

```
Secure Context - Check web server configuration (use HTTPS)
```

这个检查硬编码在 Godot 生成的 loader 里（`build/index.js`），没有开关。
所以 `certs/` 里放了一张自签证书（已 gitignore）。另一台设备第一次打开会看到
「您的连接不是私密连接」，点「高级」→「继续前往 192.168.x.x（不安全）」，之后一切正常。

**证书是自动的**：`serve.mjs` 每次启动都会比对当前局域网 IP，缺了或对不上就自动重签一张，
覆盖本机所有网卡地址。需要 openssl（Git for Windows 自带，脚本会自动去找）。
换了网络（比如去别人家）直接启动即可，不用记命令。

万一自动生成失败，手动命令是（注意 `MSYS_NO_PATHCONV`，否则 MSYS 版 openssl 会把
`/CN=...` 当路径改写）：

```powershell
$env:MSYS_NO_PATHCONV = '1'
& 'C:\Program Files\Git\usr\bin\openssl.exe' req -x509 -newkey rsa:2048 -sha256 -days 3650 -nodes `
  -keyout 'certs/lan.key' -out 'certs/lan.crt' -subj '/CN=Stick Skirmish LAN' `
  -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1,IP:<你的局域网IP>'
```

## 联机

两台设备之间**没有「一方开房间、另一方连过去」这个选项**：浏览器不能监听端口，
Godot 网页版同样不能，而 ENet（UDP）在网页版不可用。所以 `tools/serve.mjs` 兼任中继，
两个浏览器都作为客户端连上来，中继把消息转给同房间的其他连接。

中继与网页**共用同一个端口**（`ws://…:8000/ws` 与 `wss://…:8001/ws`），
目的是让自签证书只处理一次。

### 两台设备怎么玩

1. 一台跑 `node tools/serve.mjs`
2. **这台机器**打开 `http://localhost:8000/`（`localhost` 也算安全上下文，没有证书提示）
3. **另一台**打开 `https://<本机局域网IP>:8001/`（会提示证书，点「高级」→「继续前往」）
4. 两台都**左键点一下画面**（全屏 + 接管鼠标），就能看见对方的火柴人了

两边网址不带参数就都进 `game` 房间。要分开测试时用 `?room=xxx`，**房间名必须一致**。
一个人先进房间时画面中央会显示 `WAITING FOR OPPONENT` 与当前房间名，对手进来才喊 `ROUND 1`；
右上角是记分板。左上角还有一行 `room=… me=… rank=… connected` 的开发信息，
只在**没连上**或加了 `?debug=1` 时显示——正常游玩时它只是噪声。

同步由 `scripts/net.gd` 负责：每个客户端以 20 Hz 广播自己的位置、朝向、俯仰、下蹲、比分，
替身做位置平滑、并用收到的位置差算出速度来驱动步态。

替身**没有物理碰撞**（只有一层“只给射线用”的碰撞体，见下文命中判定），所以两个人可以走到一起、
互相穿过；也没做延迟补偿与断线重连——对端消失靠 2 秒超时判定。这三项是已知的取舍，
不是遗漏：局域网下它们带来的收益远小于复杂度。

位置平滑有一个例外：目标位置离替身超过 3 米（或朝向差超过 75°）时**直接瞬移**。
回合重置与重生都是瞬间换位置，那段距离做平滑只会表现为“横穿整个场地滑过去”，比瞬移更奇怪。

### 踩过的坑：握手超时只有 3 秒

`WebSocketMultiplayerPeer` 的 `handshake_timeout` 默认 **3 秒**，而且它**从创建客户端的那一刻就开始计时**，
不是从连接建立开始。如果首帧渲染耗时超过 3 秒（软件渲染、低端设备、冷启动都会），
第一次 `poll()` 时超时已过，Godot 就判定握手失败并放弃连接：

- `poll()` 一旦看到 `CONNECTION_DISCONNECTED` 就**直接返回**（`websocket_multiplayer_peer.cpp` 的 `poll()`），
  所以即使底层 WebSocket 随后真的进入了 `OPEN`，也不会有任何东西再去读它
- `_clear()` 只把 `peers_map` 置空、**不关闭底层 socket**，也不重置 `handshake_timeout`
- 症状：连上后立刻“断开”，`get_connection_status()` 是 `disconnected`，
  而内层 `WebSocketPeer` 却是 `OPEN`、关闭码为 `-1`，没有任何错误信息

`net.gd` 因此把 `handshake_timeout` 设为 **20 秒**。

### 中继约定

| 项目 | 约定 |
| --- | --- |
| 房间 | 由路径决定：`/ws` 是默认房间，`/ws/<名字>` 是独立房间，房间之间不转发 |
| 编号 | 全局递增，从 1 开始。哪个是房主由游戏按编号判断，中继不参与 |
| 控制消息 | 文本帧，以 `relay:` 开头，**只在客户端请求之后才发出** |
| 游戏数据 | 一律用二进制帧，原样转发 |
| `?as=godot` | 该连接可以运行 Godot 的 `WebSocketMultiplayerPeer` |

请求房间信息：发出 `relay:whoami`，得到 `relay:hello id=<编号> room=<房间> peers=<人数> ids=<全部编号>`。
需要离开通知：发出 `relay:subscribe`，之后同房间有人离开会收到 `relay:peer-left …`。

### 高层联机 API 的实测结论

`?as=godot` 让中继在握手之后先发出一个 4 字节小端 int32（自身编号，且 ≥ 2）。
Godot 的客户端要求第一个包就是这个内容，否则主动断开并报 `Invalid ID received from server`
（见 `modules/websocket/websocket_multiplayer_peer.cpp` 的 `_poll_client`）。

启用之后 `MultiplayerAPI` 能进入已连接状态，**广播式 `rpc()` 双向可用**（实测无重复、无丢失）。
但是 Godot 把收到的每个包都标记为「来自 1 号」，也就是发送方身份无法获知。因此：

- `rpc()`（广播）可用；需要区分发送者时，把自身编号写在参数里
- `rpc_id()` 定向到某个玩家不可用
- 按 peer 的可见性（`MultiplayerSynchronizer`）不可用，状态同步需要自己写

## 角色

角色是**骨骼绑定**的火柴人（`scripts/stick_figure.gd`），用 `Skeleton3D` 承载 12 根骨骼，
每根骨头由 `BoneAttachment3D` 挂网格，旋转骨骼就是摆动肢体。

### 身体怎么连成一体

只把四肢做成各自独立的竖杆，画面上会得到一个“头浮在躯干上方、手臂和腿是与躯干平行的
两根悬空细杆”的角色（曾经就是这样）。所以除了竖杆，还有三类连接件：

| 连接件 | 作用 |
| --- | --- |
| 骨盆横杆 | 把两条大腿接到躯干下端 |
| 肩横杆 | 把两条手臂接到躯干上端 |
| 关节球 | 填住两段圆柱转动时裂开的 V 形缝（肩、肘、髖、膝共 8 处） |

方向约定：**躯干从骨盆向上长（`+Y`），四肢从骨骼原点向下垂（`-Y`）**。
符号写反不会报错，只是那一段会挂到身体外面去（比如胸前横带跑到膝盖上），
所以自检里有一项专门验证各部件的外包围盒两两相交。

### 动画

动画不用 `AnimationPlayer`，而是按移动速度直接算骨骼角度（`animate()`）。
原因：步态需要随速度连续变化（走得快摆幅就大），用轨道资源是先量化再插值，反而更绕；
而且轨道路径写错了不会报错，只是不生效，很难发现。参数集中在脚本上方的常量里，方便调手感。

| 状态 | 动作 |
| --- | --- |
| 走路 | 大腿前后摆、膝盖向后屈、手臂反相摆、躯干前倾、身体随步伐起伏 |
| 跳跃 / 下落 | 前腿抬起、后腿后伸、双臂向后上举 |
| 停住 | 摆幅衰减到 0，回到直立站姿 |

摆幅取自水平速度，所以慢走和快跑是连续过渡的，没有"动画切换"的跳变。

### 朝向：镜头只由鼠标转，身体随方向键偏转一点

| 操作 | 效果 |
| --- | --- |
| 鼠标 | 旋转镜头（身体与外观都是它的子节点），这就是移动换算的基准 |
| W A S D | 平移，并让**身体偏转**（镜头不跟着动） |

身体偏转的规则是：**横向输入决定偏哪一侧，后退时横向镜像**。上限由 `player.gd` 的
`lean_deg` 控制（默认 45°，可调）；松手后回到直立。

| 按键 | 移动 | 身体偏转 |
| --- | --- | --- |
| W / S | 前 / 后 | 0°（直立） |
| A / WA | 左 / 左前 | 左倾 |
| AS | 左后 | **右倾** |
| D / WD | 右 / 右前 | 右倾 |
| DS | 右后 | **左倾** |

注意它**不随移动方向单调变化**（后退时镜像），因此不能用“身体朝移动方向、限幅”
这类公式表达。`net-probe-check.mjs --walk` 会逐键断言这张表（共 6 个按键组合）。

镜头不跟随这个偏转，仍然只由鼠标控制。试过让外观完全朝移动方向转、并让镜头跟着转，
结果是方向键一按画面就转，“朝屏幕里走”与 W 键的语义不再一致，操作失去参考，已回退。
若以后要再试，务必把移动换算的基准与镜头旋转分开，否则会形成正反馈
（按 D → 右转 → 镜头转 → “右”又变成新的右 → 一直转圈）。

网络同步发的是 `player.facing_yaw()`（鼠标朝向 + 身体偏转），不是 `player.rotation.y`：
身体会偏转，只发后者的话远端看到的脸朝向会差一个偏转角。

### 两套样式

| 序号 | 名称 | 特征 |
| --- | --- | --- |
| 0 | `ember` | 实心墨色头，肢体略粗，墨水色为墨黑 |
| 1 | `frost` | 纸白头带墨线，肢体略细，多一道胸前横带，墨水色为石墨灰 |

样式按**进入房间的顺序**分配：中继下发的编号是全局递增的，所以同一房间内编号的大小关系
就是先后顺序。把已知编号排序，各自的位次就是样式序号，两个客户端算出来必然一致。

头部前方有两只眼睛——火柴人的杆是轴对称的，没有它就分不出面朝哪边。
眼睛的位置按 `head_size` 比例算，两套头形只需各自给出"前表面在哪"（`eye_surface`）。

## 射击

枪（`scripts/gun.gd`）是细杆与小方块拼的，和角色一样靠“结构件 + 墨线”辨识。
枪管与机匣取主人的墨水色、握把那一系取纸白，所以枪和主人一眼能对上。

### 枪挂在右手上，且指向子弹真正飞去的方向

枪沿**本地 `-Y`** 构造（与肢体竖杆一致），所以挂到右手骨头上、手臂前伸时枪口自然朝前。
手臂的姿态要抵掉三级旋转，否则枪口会与准星错开：

| 要抵掉的旋转 | 来源 |
| --- | --- |
| 角色绕 Y 的偏身 | 方向键（最大 `lean_deg`，默认 45°） |
| 躯干绕 X 的前倾 | 步态（走路时一直存在） |
| 镜头俯仰 | 鼠标上下（枪口要跟着抬降） |

实现上不手写欧拉角，而是求“把手臂本来朝下的方向转到目标方向”的最小旋转：
欧拉顺序记错就会差 90°，而且躯干那一级很难手算。自检里有一项
「枪口始终对准子弹方向」逐组（偏身 × 俯仰）验证，实测偏差 0.0°。

这里有一个容易错的点：**“要抵消的偏身”在两种宿主下含义不同**。
`stick_figure.aim_lean` 由宿主告知，而不是让组件自己读 `rotation.y`：

| 宿主 | `rotation.y` 是什么 | 要不要抵消 |
| --- | --- | --- |
| 本地玩家 | 相对 `Player` 的偏身 | 要（`Player` 那份旋转在外层已经生效，子弹方向就在 `Player` 空间里） |
| 替身 | **自己的世界朝向** | **不要**（否则枪会恒指世界前方，与朝向无关） |

曾经就是因为它读了自己的 `rotation.y`，对手的枪永远指向同一个方向。

### 命中判定由被打中的人做

射出方**不**判定命中，它只广播“我在哪、朝哪个方向开了一枪”（枪口位置 + 指向命中点的方向）。
收到的人用**自己当前位置**重放这条射线，第一个碰到的就是自己才算中。

为什么这样选：射出方手上的目标位置是 20 Hz 同步过来的旧数据，8 m/s 时误差可达 40 厘米；
被打者用自己的真实位置判定才准，也不怕对手改客户端报假命中。代价是**没有延迟补偿**：
网络卡的时候会出现“看着打中了却没掉血”。这类取舍下一步可以再谈。

射线同时会碰到掩体，所以躲墙后是真实有效的。替身另有**只给射线用**的碰撞体
（第 3 碰撞层，不做物理阻挡），用来让曳光停在对方身上。

### 血量与重生

- 满血 100，每发 34 点，三发倒
- 自己血量在左下角，替身的血量在头顶
- 血量归零就侧倒，3 秒后在出生点重生（出生时两人面对面，而不是都朝同一侧）
- 打中别人时准星旁会闪一个 `x`——它是从**对方的血量真的掉了**推出来的，不是射出方自报

头顶血条的朝向不用 billboard 材质，而是**节点每帧转向相机**（`look_at`）：
两个方片几乎重合，只靠零点几毫米的偏移分先后；billboard 只改顶点朝向、**不改位置**，
于是那点偏移的方向随替身朝向变，再叠加 `no_depth_test`（深度完全不参与判定），
从某些角度就只看得见一个灰色矩形。现在朝向由代码掌握，填充沿“朝相机”方向前移，
前后关系由深度测试定死。代价是每帧一次 `look_at`（一个替身一次，可忽略）。

顺带去掉了 `no_depth_test`：血条因此会被墙挡住，但这比“隔着掩体看到血条”合理。

### 计分与回合（`scripts/match.gd`）

比分**由击杀事件驱动**，而不是各端自报：

1. 被打倒的人在自己的客户端最先知道结果（判定权本来就在他手上），
   于是由他广播一条 `_peer_kill(被打者, 开枪者)`
2. 中继对所有人是同一份转发，所以两端**按同一顺序**应用同一条事件，比分天然一致，
   也不需要约定“谁说了算”

周期性状态里的 `kills`/`deaths` 只在**第一次见到某个编号时**用来补种（迟进房间的人不至于看到 0:0），
之后就不再用它覆盖——否则重置回合时，迟到的旧数据会把刚清零的比分写回去。

- 到达分数上限（默认 3，可用网址参数 `?kills=N` 覆盖）时，各端**本地**用同一份比分判断出胜负，
  所以两端几乎同时进入终局，不需要再发一条“回合结束”的确认消息
- 结算横幅停留 4.5 秒，然后比分清零、回合号 +1，两人各自回到出生点并**恢复开局朝向**
- 界面：右上角记分板（名字就是样式名，`ember` / `frost`）、右上角击杀提示、屏幕上方横幅
- 一个人先进房间时显示 `WAITING FOR OPPONENT` 与房间名：两台笔记本的场景里，
  先到的那台不该对着空场地猜还要不要打开另一台；等对手出现才喊 `ROUND 1`

`reset_for_round()` 与重生（`respawn()`）的差别只有**朝向**：局中被打倒重生时不该掰回你的准星
（那会让人刚重生就被动转向），而回合开始时两边都回到面对面的初始姿态才公平。

### 开火扳机：不依赖 Godot 的动作状态

开火不是直接读 `Input.is_action_pressed("fire")`，而是由 `player._trigger_held` 自己维护。
原因是一个真实存在的故障：

> **浏览器会把“点击进入游戏”那一次的 mouseup 吞掉。**
> Mac 触控板上稳定复现（全屏过渡有一段动画，松开落在过渡期间）：点一下进游戏，
> 随后就一直开火，即使早已松开。Godot 的动作状态只由事件驱动，丢了 mouseup 就永远
> 停在“按下”，于是每帧都判定为按住不放。

自己维护之后规则很简单，而且不怕丢事件：

| 信号 | 含义 |
| --- | --- |
| 左键按下，且**已经接管了鼠标** | 开始按住。进游戏那一下因此永远不会顺手打出一发 |
| 左键松开 / 丢失指针锁定 / 窗口失焦 | 松开 |
| 浏览器侧报告“左键已抬起” | 松开（见下） |

极短的点击可能在**同一帧**里完成按下与松开（那时“按住”已经回到 false），所以另留一个
0.15 秒的脉冲，保证“点一下”总能打出一发。

### 怎么发现“那次松开被吞掉了”

Godot 自己的事件流发现不了。实测过一个看似可行的启发式：用**移动事件的按键掩码**——
手指抬起后，移动事件里的掩码应该是 0。结论是**它不成立**：Godot 网页版把这个掩码
填成自己记录的状态，而不是浏览器的 `e.buttons`；丢了 mouseup 时它一直是 1。
（`net-probe-check.mjs --fire` 的第 6 项就是量它的，所以这条写在这里而不是留在代码里当死代码。）

真正独立的信息源在浏览器那边：`export_presets.cfg` 的 `head_include` 里给左键记了两个
计数（按下、抬起各一个），并且**在 `pointermove` 里用 `e.buttons` 自我纠正**——
即使 mouseup 事件丢了，下一次移动也能把“其实已经抬起”告诉页面。
游戏在“自己认为按住”时每帧读一次这两个计数（`_dom_trigger_released()`），
不一致就松开。注入脚本不存在时（旧的导出产物）表达式返回“仍按着”，退回到原有行为。

这一整套由 `node tools/net-probe-check.mjs <url> --fire` 守着，六项断言：
用 CDP **只发 `mousePressed`、永远不发 `mouseReleased`** 就能在 Windows 上造出同样的局面。
实测旧逻辑会在那一项下连打 11 发，修好后是 0 发；另外它还守着“按住时移动不能把扳机培掉”、
“点一下仍能打出一发”这两件事。

### 后坐力与下蹲

后坐力是**真抬准星**：子弹方向取自镜头，所以枪口与弹道会一起上去，而不是只晃一下画面。

它是**累积上飘、不回落**的：连发时准星逐渐往上飘，松开后**停在抬起的位置**，
要靠自己把鼠标往下压来补偿。这比“抬一下再弹回去”更吃操作，也是压枪这门手艺的来源。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `recoil_per_shot_deg` | 1.4 | 每发抬起多少度 |
| `recoil_yaw_deg` | 0.6 | 每发**左右**随机偏移的上限（左右各取一半） |

水平那一项是**随机**的：每发独立取值，所以连发轨迹不是一条直线，而是会左右乱蹿。
它和俯仰一样累积、不回落，也要靠鼠标补回来。差别是水平方向**没有上限**
（yaw 会绕圈，硬设一个限制反而奇怪），俯仰则由 `pitch_max_deg` 封顶。

唯一的边界是俯仰上限（`pitch_max_deg`，默认 35°）：一直按住不放会飘到顶，此时无法再往上。
默认视角是 −12.6°，所以从满下限到上限约 34 发，差不多一个弹匣。

子弹飞向的是**开火前**瞄的位置，抬升留给下一发——所以连发的第一发永远和准星一致。

散布让子弹不再精确地打在准星那一点上，它跟着连发增长、停火回落：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `spread_min_deg` | 0.25 | 静止/首发时的散布半径 |
| `spread_max_deg` | 2.4 | 连发时的散布上限 |
| `spread_per_shot_deg` | 0.45 | 每发增长多少度 |
| `spread_recover_per_sec` | 3.2 | 停火后的回落速度（度/秒） |

于是点射准、扫射散。散布改的是**这一发真的飞向哪**，方向在广播之前就定下来，
远端重放的是同一条弹道（不是“远端自己再随机一次”）。下蹲会按 `crouch_recoil_scale` 一起缩小散布。
在锥体内取点时径向半径取 `sqrt(randf())`：直接取均匀随机会在中心堆叠，看起来像“子弹偏爱中间”。

### 命中表现的调味

| 表现 | 做法 |
| --- | --- |
| 准星随散布张开 | 中心的四个刻度按当前散布拉开间距。这是玩家**唯一能看见**散布的地方，否则它只是个看不见的数值 |
| 准星中心很小 | 只有 3×3 像素的一个点（`CROSS_CENTER`）。曾经是 6×6 的实心方块，实测挡视野——屏幕正中恰好是看对手的位置 |
| 枪身后退 | 开火那一帧枪沿枪管向后蹿 3 厘米再回位（纯视觉，子弹方向与枪口位置不取这个偏移） |
| 镜头抖动 | 开火 0.6 厘米、挨打 2.4 厘米，衰减约 0.15 秒。写在相机的 `h/v_offset` 上，不动 `SpringArm` 的位置与旋转 |
| 挨打反馈 | 整屏转墨（叠一层半透明黑）+ 短音 + 头顶血条，倒地时更重 |
| 倒下碎屑 | 一圈小方块向外飞散、边飞边缩（名字以 `Impact` 开头，`_count_fx()` 会把它一起数进去） |
| 对方的膛口火光 | 收到开火消息时也让他那把枪亮一下，否则只能看到曳光，看不出他从哪开火 |

一个需要注意的后果：这个相机在 2.5 米高，瞄准同高度、6 米外的对手时，
命中区间只有约 16°（−6.7° 到 −22.6°）。每发 1.4° 意味着连发四五发就会打过对方头顶，
所以实际打起来得**一边扫一边压枪**。觉得太难就把 `recoil_per_shot_deg` 调小。

按下 Shift 下蹲：

- 相机从 2.5 米降到 2.2 米，移动速度降到 45%
- **后坐力降到 35%**（这就是“蹲下换稳定”的实惠）
- 火柴人视觉上下蹲：骨盆降 0.32 米、膝盖多弯、躯干略前倾

下蹲只是**视觉上的蹲**，碰撞胶囊高度不变，所以现在钻不进矮掩体。
另外相机不能压得太低：实测降到 1.6 米时角色的头会正好压在准星上（头顶到屏幕纵向 0.48，
准星在 0.50），刚腾出来的位置又没了。现在取 2.2 米（0.56），并有断言守着这一条。

## 音效：全部由代码合成（`scripts/sfx.gd`）

不引入任何音频素材：导出预设是 `all_resources`，往项目里加 wav/ogg 会被一起打进 `index.pck`
并随页面发给局域网里每个人，而这个包本身只有一百来 KB。

启动时用正弦、噪声与指数包络合成九个 `AudioStreamWAV`（枪声、弹着、受伤、倒地、击杀、
重生、回合开场、胜利、失败）。为了能在无头环境里验证，合成被拆成三个可复用的形式：
下滑音高的爆音、极快衰减的噪声、一串定长音符。

- 别人的枪声用 `AudioStreamPlayer3D`，按世界位置衰减——这是第三人称视角下唯一的方向线索
- 自己的枪声与提示音用普通播放器：自己开枪时相机就在枪口旁边，定位只会让音量随转头忽大忽小
- 播放器“建了就忘”（`finished` 里回收），同时存在的数量有上限（24），连发时不会堆节点

音量写在 `Sfx` 各个 `play_*` 里的 `volume_db`，那是需要人耳朵调的数值（见下方“人机分工”）。

## 取景：角色在准星下方

镜头挂高到 2.5 米，角色就落在画面下半部，准星周围腾出空位看向远处：

- 头顶落在屏幕纵向约 **0.60**（0 是顶端、1 是底端），准星在 0.5
- 这个值由快照里的 `headScreenY` 给出，可以断言，不用靠眼看截图

缺点是**看不到自己角色的脸**（相机在身后），眼睛只有看到对手时才有用。

## 全屏与鼠标锁定

Godot 默认生成的 HTML 外壳**没有任何全屏能力**，所以要自己加。相关代码在
`export_presets.cfg` 的 `html/head_include` 里——一段注入到 `<head>` 的小脚本。

实际行为：

- **第一次打开页面时**画面下方写着 `CLICK TO PLAY` 与操作说明——浏览器不允许程序自己抢鼠标，
  所以“必须点一下”是硬性前提；不说这一句，第一次打开链接的人只会看到一个不会动的场地
- **点击画面** → 自动进入全屏，同时锁定鼠标（一次点击办完两件事，因为点击本身就是浏览器要求的"用户手势"）
- **按 Esc** → 释放鼠标并退出全屏，`CLICK TO PLAY` 重新出现
- Esc 之后**再点一下画面**，又回到全屏 + 锁定，可以反复

**退出全屏是浏览器自己做的，项目里没有相关代码。**
曾经写过一条 `pointerlockchange` 联动（丢指针锁就主动退出全屏），后来验证发现纯属多余——
用 CDP 把 `document.exitFullscreen` 换成空操作再按 Esc，全屏照样会退，说明浏览器原生就会处理。
既然多余，就删掉了：它多出来的那一次主动退出，反而可能在指针锁释放的同一瞬间干扰光标位置。

### 锁指针为什么不放在 GDScript 里

网页上"锁定鼠标"这一步交给注入脚本做，`player.gd` 里对 web 平台刻意不动 `mouse_mode`。

浏览器要求 `requestFullscreen()` 和 `requestPointerLock()` 都必须在用户手势里发出，
而两者**同时发出会打架**：全屏切换过程中发出的锁定请求偶尔被拒，
表现就是"点一下，全屏进去了但鼠标还显示着，得再点一次才能操作"。
实测这个竞态可以复现：同样的 点→Esc→点 序列，有时成功有时失败。

改法是让脚本把两件事串起来：先请求全屏 → 等 `fullscreenchange` → 再锁指针，并带两次重试。
Godot 会自己跟随浏览器真实的指针锁状态（实测：脚本主动锁定后，角色按键立刻可操作），
所以引擎不需要再发一次请求。

### F11 和这条路径是两回事

F11 是**浏览器自己的**快捷键，任何网页都能用，项目里没有任何相关代码。区别在于：

| | F11（浏览器全屏） | 点击画面（Fullscreen API） |
| --- | --- | --- |
| `document.fullscreenElement` | 保持 null | 被设成根元素 |
| 触发上面那条指针锁联动 | 不触发 | 触发 |
| 谁发起 | 用户按键，浏览器处理 | 页面在用户手势里请求 |

所以用 F11 进的全屏，Esc 退出靠的是浏览器自身行为，不经过我们的联动。
正常玩就走"点画面"这条路径，全屏和鼠标锁定是一起给的。

### 鼠标不会被测试困住（光标守卫）

Windows 的 `ClipCursor`（鼠标裁剪）会被浏览器进入指针锁定时用来把光标圈在窗口内，
而**还原**发生在窗口销毁的流程里。只要设限制的进程没走到那一步（被强杀、崩溃、控制台被关掉），
限制就作为孤儿留在系统里：光标被锁在某个小矩形里，而且**找遍所有窗口都找不到尺寸吻合的那个**。

早先的做法是"收尾时清理一次"，但那种保证依赖测试跑到收尾——开发中把测试输出管道接到
`Select-Object -First`（读满 N 行就掐掉上游）、或者直接打断，就漏掉了。现在改成不依赖收尾：

`tools/cursor-guard.ps1` 是一个**独立的守望进程**，在整个测试期间每 100 毫秒读一次裁剪范围，
发现被改动就立刻恢复（用 `ClipCursor(NULL)`）。它由测试脚本启动，并且**先于浏览器**启动，
所以它拿到的基准值是"没被裁剪"的真值。

| 情况 | 结果 |
| --- | --- |
| 测试正常运行 | 光标在整个测试期间都不会被困超过一个采样间隔（实测 110～122 毫秒，每次测试只触发 1 次） |
| 测试被强杀 / 崩溃 / 管道被掐断 | 守望进程发现父进程消失，清掉残留的测试 Chrome、再解除一次裁剪，然后自己退出 |
| 剩余风险 | 只剩"强杀发生在被裁剪后的 100 毫秒之内"这个窗口，肉眼不可感 |

验证与手动使用：

```powershell
# 自检：人为把系统置成"被裁剪"那个坏状态，看守卫能否在一个采样间隔内恢复
powershell -ExecutionPolicy Bypass -File tools/cursor-guard-check.ps1

# 整个开发时段的手动守护（例如边改代码边用浏览器试玩）
node tools/cursor-guard.mjs --minutes 60

# 万一手动驱动浏览器时还是被困住了
powershell -ExecutionPolicy Bypass -File tools/free-cursor.ps1
```

急用的话也可以按 **Ctrl+Alt+Del**（那个界面会强制解除系统层面的捕获），再按 Esc 退出。

测试脚本收尾时的顺序是：让页面 `exitPointerLock` → 让页面自己关闭（**不**用 `taskkill /F`，
强杀会跳过浏览器还原裁剪的那段流程）→ 兜底清一次 → 最后停守卫并读它的统计。
统计里有两项是断言：离开时的裁剪范围必须与启动时的基准一致、单次被圈住的时长不超过 500 毫秒。

两条由此而来的自纪律（写在这里免得再犯）：

- **不要把测试脚本的输出管道接到 `Select-Object -First N`**：它在读满 N 行时会掐断上游，
  等于把这个测试在随机时刻强杀。要截取输出就写进日志文件再读。
- 强化浏览器时（比如自己写的 CDP 脚本）也要**先**起守卫，或者收尾时手动跑一次 `free-cursor.ps1`。

## 操作

| 操作 | 键位 |
| --- | --- |
| 全屏 + 锁定鼠标 | 点击画面 |
| 释放鼠标 + 退出全屏 | Esc |
| 移动 | W A S D / 方向键 |
| 跳跃 | 空格 |
| 视角 | 鼠标 |
| 开火 | 鼠标左键（按住连发，约 9 发/秒） |
| 下蹲 | Shift（按住） |

**点击进入游戏的那一下不会开火**：那一次点击是用来锁定指针的。`player.gd` 里有
`FIRE_BLOCK_AFTER_CAPTURE`（0.25 秒）来保证这一点，`--shoot` 模式会断言它。

**键盘只在鼠标被锁定（也就是"正在操作游戏"）时才生效。** 光标还露在外面时按 W 不会让角色移动。
判定标准是 `Input.mouse_mode == MOUSE_MODE_CAPTURED`，见 `player.gd` 的 `_input_active`。

进入游戏的方式只有一种：**左键点击画面**。
注意滚轮不算——Godot 里滚轮也是 `InputEventMouseButton`（`button_index` 为 4/5）且 `pressed` 为 true，
如果不校验按键类型，滚一下滚轮就会把游戏激活。

同理，切走标签页时 `keyup` 收不到，按键会卡在"按下"状态；`_notification()` 里监听
`NOTIFICATION_APPLICATION_FOCUS_OUT` 主动清掉按键并停下角色，否则切回来一点画面角色就自己走了。

## 已知坑

- **本项目所在的这台机器 `github.com:443` 不通**（DNS 正常，API 与 CDN 通）。
  编辑器里「管理导出模板」的自动下载会失败，需要走 `api.github.com/repos/.../releases/assets/<id>` 取 302 再抓。
- 网页导出用单线程模式（`variant/thread_support=false`），因此不需要 COOP/COEP 跨域隔离响应头。
- **`CollisionShape3D` 必须是 `CollisionObject3D` 的直接子节点。** 中间夹一层 `Node3D` 时物理引擎不报错、
  但完全不注册该形状——表现是角色穿过地板一直往下掉。`arena.gd` 里因此把网格和碰撞形状都直接挂在
  `StaticBody3D` 下。
- **浏览器不允许程序主动抢鼠标锁定。** `_ready()` 里设 `Input.mouse_mode = MOUSE_MODE_CAPTURED`
  会抛 `WrongDocumentError`，必须等玩家第一次点击（见 `player.gd` 的 `_unhandled_input`）。
- 导出前记得 `build/` 目录要存在，Godot 不会自动创建。
- **另一台设备必须用 HTTPS 打开**，明文 HTTP 的局域网地址会报 Secure Context 错误（见上）。
- **无头浏览器里指针锁会失败**，报 `WrongDocumentError: The root document ... not valid for pointer lock`。
  原因是无头模式默认不给页面前台焦点。用 CDP 测试时先发一次 `Page.bringToFront`、
  确认 `document.hasFocus()` 为 true，指针锁就正常了。真浏览器里不存在这个问题。
- **打包体积卡住了 Cloudflare 这条路**：Pages 和 Workers 静态资源的单文件上限都是
  **25 MiB**，而 `index.wasm` 有 **37.7 MiB**，直接超限。官方建议改用 R2 桶，
  或者把 wasm 预先 gzip 成 9.7 MB 再让 Worker 补 `Content-Encoding: gzip` 头。
  再加上 `github.com` 不通、`*.workers.dev` 在国内可达性不确定，本次没有走云部署。
